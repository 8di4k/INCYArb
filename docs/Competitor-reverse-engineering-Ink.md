# Поиск площадок через реальные исполнения на Ink

22 октября 2026 UTC. Поиск через исполнителей дополняет каталог площадок:
реальные вызовы показывают источник финансирования, доступные конкретному
контракту маршруты, комиссии и расчёты. Это не требует опубликованных исходников
всего исполнителя или доступа к его серверу.

## Проверенный пример

[Транзакция `0xb245…57d8`](https://explorer.inkonchain.com/tx/0xb245d3c599153f3f0d748f111d17544bf167cabb3e31b146407ae0a7775c57d8),
блок `59203517`, исполнитель `0x1b53d396632b9528598de58bd01f721ef194a19e`.
Receipt отдельно перечитан через RPC и сверён с неизменившимся hash блока
`0x9c97e9a5dde63ad67c1b8478f0281f492ae00bbd8465bc6c2e82da7de2bd3ea6`.

Экономический круг — USDG → wTSLAx → wSPYx → USDG. Фактический порядок
вызовов использует вложенные callbacks и v4 unlock, поэтому отличается от
простого последовательного обхода стрелок:

1. Uniswap v3 `0x06fb000fe9c6505eb3b2cdf52445d8c7d5690f47` отправляет
   исполнителю **12,422258 USDG**; callback позволяет рассчитаться позже.
2. Внутри callback исполнитель использует v4-пул wTSLAx/wSPYx с AegisHook
   `0xe449e013004db4a5681e9622ca10c5ba0ea610cc`. **0,016277266125375361 wSPYx**
   отправляется из PoolManager в первый v3-пул, закрывая его требование.
3. V3-пул `0x09444cbdff5cd4437150a1f26865a3ed85d8ed5e` выдаёт
   **0,033129046577395208 wTSLAx** за **12,419849 USDG**.
   **0,033129002604429312 wTSLAx** поступает PoolManager для погашения дельты.
4. **0,002409 USDG** переводится из исполнителя в
   `0xf5d416fe576297ec930485aac489b1748bfe96b5`; остаётся небольшая wTSLAx-пыль.

Gas used: **436648**, effective gas price **1000280 wei**, L1 fee
**2943801597 wei**. Суммарный расход по receipt:
`436648 * 1000280 + 2943801597 = 439714063037 wei ETH`, или
**0,000000439714063037 ETH**. L1-компонент не прибавляется к explorer `fee`
повторно: там уже отражена эта полная сумма.

Выплата USDG и расход ETH приведены отдельно. Это не расчёт net в одной
валюте и не доказательство доходности всей работы исполнителя. Нужны также
неудачные попытки, собственные переводы/остатки, ценовая конверсия и расходы
за исследуемый период. Связь payout-адреса с отправителем вне этой транзакции
здесь не устанавливалась.

Это конкретное исполнение проходит через AMM; отдельной оракульной площадки
в нём не обнаружено. Оно не меняет целевую стратегию на pool-only. Перед
обменами видны slot0/StateView reads; предполагаемые state guards в packed
calldata требуют отдельного разбора bytecode или negative-control replay.
Трасса сама по себе не раскрывает серверный поиск, задержку, приватный канал
доставки или право другого контракта получить такие же условия.

## Что найдено в выборке

Из двух ранее проверенных captures: **296** различных блоков, **1353**
различные транзакции. Начальный фильтр выделил **43** успешные транзакции
с двумя и более стандартными AMM Swap events, **13** разных outer recipients.
Для одного представителя каждого получены public explorer raw call trace и
metadata; root from/to/input совпадают между этими источниками и связаны с
сохранёнными raw transactions. Не все эти адреса считаются арбитражниками:
среди кандидатов есть routers/aggregators и обычные составные обмены.

[Данные и полные трассы](validation/competitor-traces/capture-and-traces.json.gz)
сохраняют raw transactions, stream receipts, результаты прежней sealed-сверки,
43 кандидата, 13 explorer traces и отдельно RPC-перепроверенный receipt примера.
Explorer `raw-trace` — отдельный источник, а не результат собственного EVM replay.
RPC `debug_traceTransaction` через проверенный endpoint был недоступен (HTTP 403).

В другом кандидате
[`0x39c7…0360`](https://explorer.inkonchain.com/tx/0x39c750dbc3de362d8f0dbffad3ac98ba43863e6c43ee47fde9b8837061bd0360)
видны обмены wTSLAx/USDG через v4 с ранее неразобранным hook
`0x26b86c03bd6576b8661d53a48d70faf8c85b8044` и через v3. Успешное исполнение
показывает фактический путь доступа этого исполнителя, но не удостоверяет
оракульную модель неизвестного hook или доступ нашего контракта.

## Как продолжать поиск

Дополнительный отбор без стандартных AMM Swap events уже дал
[исполненный xChange RFQ и точный AtomicSwap deployment](Xchange-observed-Ink.md).
Это технически подтверждённая RFQ-сторона с allowlist, не публичный oracle edge.

Фильтр «два стандартных Swap» — только начальный seed. Он может пропустить
самые нужные oracle↔AMM и oracle↔oracle круги, если площадка не публикует
такие события. Следующий проход должен включать один AMM swap плюс неизвестный
обменный вызов, а также замкнутые token flows без стандартных Swap events.

Для повторяющихся исполнителей нужно восстановить полный набор площадок,
callbacks, fee/access checks и выплаты; отделить коммерческие venues от
token proxies, fee managers и агрегаторных обёрток. Затем проверить полный
круг от нашего исполнителя с фактическими комиссиями. Обнаруженный механизм
можно воспроизвести в своей реализации; копирование чужой calldata не даёт
его условий доступа, текущего состояния рынка или гарантии результата.
